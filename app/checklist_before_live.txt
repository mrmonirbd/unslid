SECTION 1 — 🔴 CRITICAL BLOCKERS (app will not work correctly without these)
────────────────────────────────────────────────────────────────────────────────

[ ] 1.1  Switch NextJS from dev mode to production build
         WHY:  Current docker-compose.yml uses `target: dev` which runs
               `npm run dev` — not suitable for real traffic, very slow.
         HOW:  In docker-compose.yml (or docker-compose.prod.yml):
               - Change `target: dev` → `target: runner`
               - Change `NODE_ENV=development` → `NODE_ENV=production`
               - Remove the source volume mount:
                   `- ./servers/nextjs:/app`  ← delete this line
               - Remove the node_modules volume:
                   `- nextjs_nm:/app/node_modules`  ← delete this line
               - Pass NEXT_PUBLIC_* vars as build ARGs (they are baked at build time)
         FILE: docker-compose.yml → nextjs service

[ ] 1.2  Set ENVIRONMENT and APP_DOMAIN correctly
         WHY:  Currently ENVIRONMENT=development causes Stripe to redirect users
               back to http://localhost after checkout — breaks on a real server.
         HOW:  In .env (production copy):
               ENVIRONMENT=production
               APP_DOMAIN=app.yourdomain.com
         FILE: .env

[ ] 1.3  Add a reverse proxy with SSL (Nginx or Caddy)
         WHY:  Ports 3000 and 8000 are exposed directly. Production needs HTTPS
               and a single entry point on port 443.
         HOW:  Recommended — use Caddy (simplest, auto SSL via Let's Encrypt):
               - Create a Caddyfile in the project root
               - Add a caddy service to docker-compose.yml
               - Caddy routes app.yourdomain.com → nextjs:3000
               - Caddy auto-renews Let's Encrypt certificates
         ALTERNATIVE: Nginx + Certbot (more config, same result)

[ ] 1.4  Change the PostgreSQL password
         WHY:  Currently hardcoded as "localdevpass" — must never be used in prod.
         HOW:  Generate a strong password:
               python3 -c "import secrets; print(secrets.token_urlsafe(32))"
               Update in docker-compose.yml:
                 POSTGRES_PASSWORD: <new-strong-password>
               Update DATABASE_URL in fastapi and worker services to match.
         FILE: docker-compose.yml

[ ] 1.5  Point your DNS to the VPS
         HOW:  In your domain registrar / DNS provider:
               - A record: app.yourdomain.com → <VPS IP address>
               - A record: yourdomain.com     → <marketing site IP> (if separate)
               Wait for DNS propagation (up to 48h, usually <30 min)

SECTION 2 — 🟡 IMPORTANT (won't stop the app but needed for full functionality)
────────────────────────────────────────────────────────────────────────────────

[ ] 2.1  Register Stripe webhook
         WHY:  Plan upgrades (free→pro, pro→team) are applied via webhook.
               Without it, users pay but their plan never changes in the DB.
         HOW:  In Stripe Dashboard → Developers → Webhooks → Add endpoint:
               URL: https://app.yourdomain.com/api/v1/webhooks/stripe
               Events to listen for:
                 - checkout.session.completed
                 - customer.subscription.updated
                 - customer.subscription.deleted
                 - invoice.payment_failed
                 - invoice.paid
               Copy the "Signing secret" (whsec_...) and enter it in:
               Admin Panel → Payment Settings → Webhook Signing Secret

[ ] 2.2  Configure Stripe keys in Admin Panel
         HOW:  Log in as admin → go to /admin → Payment Settings:
               - Set mode to "Live" (use live keys, not test keys)
               - Enter Publishable Key (pk_live_...)
               - Enter Secret Key (sk_live_...)
               - Enter Webhook Signing Secret (whsec_...)
               Then go to Plan Pricing & Features:
               - Enter Stripe Price IDs for Pro Monthly, Pro Annual,
                 Team Monthly, Team Annual

[ ] 2.3  Set up Resend for email delivery
         WHY:  Invite emails, welcome emails, payment failure notices are all
               silently dropped without a real email provider.
         HOW:  Sign up at resend.com → create API key → add to .env:
               RESEND_API_KEY=re_...
               EMAIL_FROM=hello@yourdomain.com
               Verify your sending domain in Resend dashboard.

[ ] 2.4  Set up Sentry for error monitoring
         WHY:  Without this you are flying blind — no visibility into crashes
               or exceptions in production.
         HOW:  Sign up at sentry.io → create two projects (Python + Next.js):
               SENTRY_DSN_FASTAPI=https://...@sentry.io/...
               SENTRY_DSN_NEXTJS=https://...@sentry.io/...
               Add to .env

[ ] 2.5  Set legal domain
         WHY:  ToS and Privacy Policy links in signup and cookie banner
               currently point to https://yourcompany.com (placeholder).
         HOW:  In .env:
               NEXT_PUBLIC_LEGAL_DOMAIN=https://yourdomain.com
               Make sure /terms and /privacy exist on that domain.

[ ] 2.6  Configure AI models in Admin Panel
         HOW:  Log in as admin → /admin → AI Model Configuration:
               - Set provider and API key for Free plan
               - Set provider and API key for Pro plan
               - Set provider and API key for Team plan
               - Optionally enable "user override" toggles for Pro/Team

[ ] 2.7  Delete or reset demo accounts
         WHY:  The demo accounts (admin@, free@, pro@, team@, member@ aipresentation.dev)
               are development-only and should not exist in production.
         HOW:  Either:
               a) Use a fresh Supabase project for production (recommended)
               b) Delete the demo users in Supabase Auth dashboard
               c) Change all demo passwords to something unguessable
         FILE: demo_accounts.txt (do not commit this file to git)

[ ] 2.8  Set a strong SECRET_KEY for encryption
         WHY:  This key encrypts all API keys stored in the database.
               If lost, all saved keys must be re-entered.
         HOW:  Generate once, store safely:
               python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
               Add to .env: SECRET_KEY=<generated-key>
               NEVER rotate this after data is in the database.

SECTION 4 — 🔵 VPS SETUP STEPS (one-time server provisioning)
────────────────────────────────────────────────────────────────────────────────

[ ] 4.1  Provision a Linode VPS
         Recommended spec for starting out:
         - 4 GB RAM, 2 vCPUs, 80 GB SSD (Linode Shared 4GB — ~$24/month)
         - Ubuntu 22.04 LTS
         - Enable backups

[ ] 4.2  Install Docker and Docker Compose on the VPS
         sudo apt update && sudo apt install -y docker.io docker-compose-plugin
         sudo usermod -aG docker $USER

[ ] 4.3  Clone the repository onto the VPS
         git clone <your-repo-url> /opt/aipresentation
         cd /opt/aipresentation

[ ] 4.4  Create the production .env file on the VPS
         Copy .env, update all values for production (see sections above)
         chmod 600 .env   ← restrict file permissions

[ ] 4.5  Build and start the containers
         docker compose -f docker-compose.yml up -d --build

[ ] 4.6  Set up automatic container restart on VPS reboot
         Docker's restart policies handle this automatically.
         Verify with: docker compose ps

[ ] 4.7  Set up a firewall
         Only expose ports 80 and 443 publicly:
         sudo ufw allow 22    # SSH
         sudo ufw allow 80    # HTTP (redirects to HTTPS via Caddy)
         sudo ufw allow 443   # HTTPS
         sudo ufw enable
         Note: Do NOT expose 3000 or 8000 publicly — Caddy handles routing.

PHASE 2A — DESKTOP APP (Installable Mac & Windows)
────────────────────────────────────────────────────────────────────────────────

  BACKGROUND:
  The original Presenton codebase was a desktop app built with Electron,
  packaging Next.js and FastAPI into a single downloadable installer (.dmg /
  .exe). The SaaS modifications (Supabase Auth, PostgreSQL, Redis, Stripe,
  multi-tenant data model) broke compatibility with the desktop build pipeline.
  Phase 2A restores desktop capability as a separate "offline/personal" tier.

  TARGET USERS:
  - Users who want a private, fully offline installation (air-gapped)
  - Users who prefer a native desktop experience
  - Enterprise customers who cannot use cloud services

  TECHNICAL APPROACH:
  The desktop version will be a "lite" single-user build from the same codebase,
  controlled by a BUILD_TARGET=electron environment variable. Key differences:

  [ ] P2A-1  Strip multi-tenant auth for desktop build
             - Replace Supabase Auth with a local session (no login required)
             - Or offer optional single-user local account
             - Controlled via BUILD_TARGET=electron flag in Next.js

  [ ] P2A-2  Replace PostgreSQL with SQLite for desktop
             - Use SQLite via SQLAlchemy sync driver (no Docker needed)
             - All new models (BrandKit, SlideComment, PresentationVersion, etc.)
               must be tested with SQLite dialect

  [ ] P2A-3  Remove Redis / ARQ dependency for desktop
             - Background tasks run synchronously or via Python threading
             - No worker container needed

  [ ] P2A-4  Remove Stripe billing for desktop
             - Desktop version uses a one-time purchase or is free/open-source
             - Remove all billing routes from desktop build

  [ ] P2A-5  Bundle all services into Electron
             - FastAPI compiled to single binary via PyInstaller (server.spec
               already exists in /electron/servers/fastapi/server.spec but
               needs updating for new models and dependencies)
             - Next.js built with BUILD_TARGET=electron (static or server mode)
             - Electron app starts both services on launch, stops on quit

  [ ] P2A-6  Desktop sync with SaaS cloud (optional post-desktop)
             - Allow desktop users to optionally connect a cloud account
             - Two-way sync of presentations between local and cloud
             - Conflict resolution strategy (last-write-wins or manual merge)
             - This was the original "post-launch sync" feature discussed earlier

  [ ] P2A-7  Code-sign and notarise macOS build (.dmg)
             - Requires Apple Developer account ($99/yr)
             - Use electron-builder with notarisation scripts

  [ ] P2A-8  Windows installer code-signing (.exe)
             - Requires an EV Code Signing Certificate
             - Use electron-builder NSIS target

  [ ] P2A-9  Auto-update mechanism for desktop app
             - Use electron-updater (electron-builder built-in)
             - Host update manifests on S3 or GitHub Releases

  EFFORT ESTIMATE: 6–10 weeks (2 engineers)
  DEPENDENCY: SaaS version must be stable and generating revenue first
